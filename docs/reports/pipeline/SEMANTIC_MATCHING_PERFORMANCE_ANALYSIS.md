# 语义匹配阶段耗时根因分析

分析日期：2026-07-24

> 2026-07-24 更新：本文建议的“先粗召回、后候选视频向量”第一阶段优化已经实施。方案、配置、真实样本召回验证与性能预期见 `SEMANTIC_MATCHING_OPTIMIZATION_PLAN.md`。

## 1. 结论

当前语义匹配阶段耗时长的根本原因不是 Python 余弦相似度、候选排序或 LLM 精排，而是：

> **在便宜的文本召回缩小候选集之前，系统对全部 52 个镜头逐个执行了云端直接视频 Embedding。**

真实任务 `c54d074d53d34a4eaa4273d61592b95b` 的阶段 6 耗时 **678.480 秒（11 分 18 秒）**，占任务处理总耗时 1128.936 秒的 **60.1%**。其中约 **638 秒、94.0%** 消耗在 52 个镜头的云端视频向量生成。

这是一项为提高画面语义召回质量而引入的高成本路径：它能弥补单帧 Vision 标签不完整的问题，但当前执行顺序和缓存粒度使其成为首轮任务的绝对瓶颈。

## 2. 证据范围

主样本：

- 任务：`data/tasks/c54d074d53d34a4eaa4273d61592b95b/`
- 输入：48 个视频、约 471.23 秒素材
- 阶段 3：52 个镜头
- 阶段 5：9 个播音单元、12 个视觉节拍
- 视频向量配置：启用、0.5fps、最大 10240 video tokens、并发 4
- 阶段 6：678.480 秒
- 全任务：1128.936 秒

历史对照：引入全镜头直接视频 Embedding 之前，同一类 48 素材任务的阶段 6 分别为 15.228、19.023、32.867 秒，均值 22.373 秒。当前耗时约为历史均值的 **30.3 倍**。虽然当前检索算法也增加了视觉节拍和混合召回，受控子步骤实测仍证明主要增量来自视频向量分支。

## 4. 根因一：昂贵的视频理解发生在候选缩减之前

`build_match_plan()` 当前按以下顺序执行：

1. 为 12 个视觉节拍生成文本查询向量；
2. 为 52 个镜头元数据生成文本语料向量；
3. 为 12 个视觉节拍再生成视频检索查询向量；
4. **为全部 52 个镜头制作代理视频；**
5. **为全部 52 个代理视频请求云端多模态 Embedding；**
6. 才计算 12×52 的相似度并选 Top-K/词法救援候选；
7. 最后将候选提交给 LLM 精排。

因此昂贵操作的复杂度是 $O(全部镜头数)$，而不是 $O(文本粗排后的候选镜头数)$。即使某镜头完全不可能进入任何视觉节拍的候选列表，也会先支付视频切片、Base64 上传和云端多模态推理成本。

这是最核心的算法顺序问题。

## 5. 根因二：单个普通视频向量请求本身约需 50–60 秒

对同一 Provider 做了 4 个代表性镜头的并发实测：

| 镜头时长 | 代理文件大小 | 单请求耗时 |
|---:|---:|---:|
| 1.767 秒 | 0.27 MB | 5.993 秒 |
| 9.233 秒 | 1.59 MB | 54.033 秒 |
| 15.467 秒 | 1.98 MB | 59.806 秒 |
| 23.133 秒 | 1.63 MB | 53.535 秒 |

4 个请求并发执行的墙钟时间为 59.809 秒。除极短镜头外，9–23 秒镜头的延迟稳定在约 54–60 秒，说明主要成本是远端视频解码/多模态推理和服务排队，而不是本地余弦计算。

本样本镜头分布：

- 共 52 个；
- 中位时长 8.416 秒；
- P90 14.400 秒；
- 31 个镜头至少 8 秒；
- 仅 2 个镜头短于 3 秒。

并发上限为 4，因此 52 个镜头至少形成 **13 批**。每批约 50 秒时，理论墙钟约为 650 秒，与实际约 638 秒高度吻合。

## 6. 根因三：全素材被再次编码并完整 Base64 上传

阶段 6 制作的 52 个代理片段：

- 覆盖时长：471.233 秒，基本等于整套素材；
- 代理规格：640×360、10fps、H.264；
- 文件总量：63.73 MB；
- Base64 后仅视频正文约 84.97 MB，尚未计入 JSON 和元数据；
- Provider 参数只要求 0.5fps，估算实际采样约 264 帧，但客户端仍上传了 10fps 的完整压缩视频。

也就是说，为让服务端按 0.5fps 取帧，客户端先生成并传输了包含约 20 倍帧率的完整代理文件。这里同时存在：

1. 约 20 秒本地 FFmpeg 重编码；
2. 约 85 MB Base64 JSON 传输；
3. 服务端完整视频解析与多模态推理。

本地转码只占约 3%，远端推理仍是主因，但当前代理格式扩大了传输与解析负担。

## 7. 根因四：并发有限且长尾请求会阻塞整个批次

视频 Embedding 并发为 4。`asyncio.gather()` 必须等待所有镜头结束后才能继续 LLM 精排，因此阶段墙钟由最慢批次决定。

本次结果为 51/52：阶段 6 的镜头 50 没有进入视频向量缓存，回退到了文本向量。视频请求默认最多尝试 3 次，并使用 1、2 秒指数退避；当前环境只有 1 个 Embedding API Key，所以重试仍落到同一个 Key。

更重要的是，`embed_video_corpus()` 捕获单镜头异常后只返回 `None`，没有记录：

- 失败类型；
- 每次尝试耗时；
- HTTP 状态码；
- Provider request ID；
- 是否发生超时或限流。

因此可以确认一个镜头最终失败并可能产生重试长尾，但现有日志无法恢复其准确贡献。

## 8. 根因五：缓存只在任务内、整批结束后写入，首轮几乎无法受益

`video_embeddings.json` 位于单个任务目录中：

- 新任务即使上传完全相同的素材，也会重新生成全部视频向量；
- 文本重剪直接复用阶段 1–6，不会再次进入该缓存读取路径；
- 缓存在整批 `gather()` 完成后一次性写入，而不是每完成一个镜头就 checkpoint；
- 如果进程在 52 个请求中途退出，已成功的昂贵请求不会被持久化；
- 当前缓存仍缺少镜头 50，若同任务重跑阶段 6，还会再次尝试该镜头。

因此现有缓存能降低“同一任务原地重复执行阶段 6”的成本，但正常首轮处理和跨任务复用基本得不到收益。

## 9. 次要原因：大量远端请求串行分组执行

Volcengine 文本/多模态 Embedding Provider 不是一次批量提交多个文本，而是每个文本一个 HTTP 请求，然后用 Semaphore 控制并发。

当前首轮阶段 6 至少包含：

| 请求组 | 逻辑条数 |
|---|---:|
| 视觉节拍文本查询 | 12 |
| 镜头元数据语料 | 52 |
| 视频检索查询 | 12 |
| 镜头视频语料 | 52；其中失败镜头最多尝试 3 次 |
| 同期声稿件句子 | 9 |
| 同期声候选分句 | 29 |

在仅一个视频镜头最终失败且其他请求均首次成功的理想假设下，仍至少产生 **168 次 Embedding HTTP 尝试**，另有 1 次 LLM 精排。

而且这些请求组按代码顺序依次 `await`：文本查询 → 文本语料 → 视频查询 → 视频切片 → 视频语料 → LLM → 同期声。很多相互独立的工作没有重叠执行。这会额外增加约 20–40 秒，但不是 11 分钟主耗时的来源。

## 10. 实测：哪些部分不是根因

使用当前 Provider 和同一任务数据，对视频语料分支之外的子步骤做了受控实测：

| 子步骤 | 规模 | 耗时 |
|---|---:|---:|
| 文本查询 Embedding | 12 | 3.656 秒 |
| 镜头文本语料 Embedding | 52 | 3.239 秒 |
| 视频检索查询 Embedding | 12 | 0.854 秒 |
| 同期声稿件 Embedding | 9 | 1.010 秒 |
| 同期声分句 Embedding | 29 | 2.150 秒 |
| 本地混合召回 | 12×52、2048 维 | **0.160 秒** |
| 本地同期声比较 | 9×29、2048 维 | **0.077 秒** |
| LLM 批量精排 | 12 个视觉节拍、128 个候选引用、约 57 KB JSON | 10.630 秒 |

结论：

- 本地向量计算和排序合计不到 0.3 秒；
- LLM 精排约 10.6 秒，不是 11 分钟瓶颈；
- 文本 Embedding 和同期声匹配合计约 10 秒量级；
- 不执行冷启动视频语料生成时，当前阶段 6 的主体成本约 **22 秒**，与历史 15–33 秒一致。

## 11. 根因优先级

| 优先级 | 根因 | 估计贡献 |
|---|---|---:|
| P0 | 对全部镜头执行云端直接视频 Embedding | 约 638 秒 / 94.0% |
| P1 | 每镜头约 50–60 秒、并发仅 4，形成 13 个批次 | 决定 P0 的墙钟形态 |
| P1 | 缓存仅任务内且整批末尾写入 | 使每个新任务重复支付 P0 |
| P2 | 10fps 完整代理上传给 0.5fps 服务端采样 | 20 秒转码 + 约 85 MB Base64 数据 |
| P2 | 单镜头重试和长尾、错误被吞掉 | 本次至少 1 个最终失败，准确耗时不可见 |
| P3 | 文本/视频/同期声请求组完全串行 | 额外约 20–40 秒 |
| 非根因 | Python 余弦、词法匹配、排序、Pydantic/JSON | < 0.3 秒本地计算 |
| 非主因 | 一次 LLM 批量精排 | 约 10.6 秒 |

## 12. 在保证匹配效果前提下的方向

不建议直接关闭视频 Embedding；它是为解决单帧 Vision 标签缺失和具体实体召回问题而加入。正确方向是减少重复、缩小昂贵推理范围，而不是回退质量：

1. **先便宜召回、后视频向量**：先用镜头文本、OCR、ASR、关键帧和词法召回形成候选并集，只对候选镜头做直接视频 Embedding，再二次排序。
2. **建立内容寻址的跨任务缓存**：按源视频哈希 + 入出点 + 模型 + fps + tokens 缓存，重复素材无需再次调用 Provider。
3. **增量 checkpoint**：每完成一个镜头立即原子写缓存，失败恢复只补缺失项。
4. **复用已有视觉资产**：阶段 4 已抽取 5 帧接触图；可评估使用多帧图像 Embedding 作为一级视频语义，只有歧义候选再提交完整视频。
5. **降低代理冗余**：直接制作接近 Provider 采样率的代理或关键帧序列，避免为 0.5fps 需求上传 10fps 视频；必须做质量回归。
6. **独立配置并验证并发**：在 Provider 配额允许时提高视频并发，但应先记录 429、P50/P95、request ID 和失败率；仅加并发不能解决重复全量推理。
7. **并行独立子链**：文本查询/语料、视频查询、代理准备和同期声向量可适度流水化，把剩余约 20–40 秒继续压缩。
8. **补齐 Provider 级可观测性**：记录每镜头上传字节、时长、尝试次数、请求耗时、状态码和 request ID，避免再次只能从总阶段倒推。

## 13. 直接视频 Embedding 是否真正改善召回

结论是：**有可测量的正向帮助，但属于“精确镜头召回和排序改善”，不是所有语义类别都依赖它；当前全量执行的时间成本远高于边际收益。**

### 13.1 消融口径

以已人工验收的改进成片所采用的 12 个视觉节拍镜头为参考，将其按源文件名和精确入出点映射到任务 `c54d074d...` 的镜头 ID。比较三种检索：

1. **纯文本**：视觉节拍文本查询向量 × 镜头 Vision/OCR/ASR 元数据向量；
2. **仅视频检索 Query 指令**：查询端使用当前 text+video 指令，但镜头仍只有文本向量；
3. **完整视频融合**：查询端融合，镜头端按当前权重融合直接视频向量。

三种方案都保留相同的 Top-10 稠密召回和最多 4 个词法救援候选，避免把词法增强误算成视频向量收益。

### 13.2 结果

| 指标 | 纯文本 | 仅 Query 指令 | 完整视频融合 |
|---|---:|---:|---:|
| 参考镜头 Dense Top-10 命中 | 9/12 | 9/12 | **11/12** |
| 参考镜头最终候选集命中 | 10/12 | 10/12 | **12/12** |
| 5 个显式实体节拍 Dense Top-10 | 4/5 | 4/5 | **5/5** |
| 5 个显式实体节拍最终候选集 | 4/5 | 4/5 | **5/5** |
| 参考镜头平均稠密排名 | 6.92 | 7.33 | **5.17** |
| MRR | 0.598 | 0.514 | **0.711** |

仅改变查询指令没有产生收益，反而略降；提升来自镜头端的直接视频向量，而不是提示词差异。

### 13.3 具体新增召回

- **新能源汽车节拍**：人工验收镜头 49 从纯文本第 13 名升到视频融合第 7 名，由候选集外进入候选集；这是最明确的显式实体收益。
- **主办/协办与市集纽带节拍**：参考镜头 14 从纯文本第 13 名（仅 Query 指令第 14 名）升到第 5 名，也由候选集外进入候选集。
- **赶集购年货**：参考镜头 11 从第 3 名升到第 1 名。
- **灌阳油茶**：参考镜头 35 从第 2 名升到第 1 名，但纯文本方案已经通过 ASR 元数据和词法救援召回，因此视频向量不是该案例修复的必要条件。
- 腊肉、酒类礼盒、寿司、开场信息卡等节拍在纯文本下已经位于第 1 名，视频向量没有新增召回价值。

### 13.4 为什么“召回提高”不等于“最终成片必然提高”

完整视频融合让 12/12 参考镜头进入候选集，但本次 LLM 最终只选择了其中 6/12 个精确参考镜头。尤其：

- 汽车参考镜头 49 已进入候选，LLM 最终选择了另一个汽车镜头 19；
- 主办/协办参考镜头 14 已升至稠密第 5 名，LLM 仍返回 null，后续使用了 fallback 镜头 50。

因此视频 Embedding 解决的是“让好镜头有资格进入候选池”，无法独立解决 LLM 全局编排、候选描述歧义和低置信选择问题。

该消融只有一套 48 素材、12 节拍样本，且精确镜头指标比“同类别任一合格镜头”更严格，不能当作通用统计结论。但它足以证明直接视频向量并非零收益，同时也证明大多数节拍已有文本/OCR/ASR/词法召回支撑。

### 13.5 收益与成本判断

- 收益：最终候选精确召回从 83.3% 提升到 100%，新增 2 个参考镜头；Dense Top-10 从 75.0% 提升到 91.7%。
- 成本：约 638 秒，占阶段 6 的 94%，即为每个新增参考镜头约支付 319 秒首轮延迟。

进一步检查“先文本粗召回、再生成视频向量”的候选并集：

| 每节拍文本 Dense K（另加最多 4 个词法救援） | 跨 12 节拍候选并集 | 参考镜头召回 |
|---:|---:|---:|
| 5 | 32/53 | 9/12 |
| 10 | 37/53 | 10/12 |
| 15 | 43/53 | **12/12** |
| 20 | 45/53 | **12/12** |

至少在本样本中，先取文本 Top-15 并集后只对 43 个镜头生成视频向量，已经保留全部人工参考镜头，可直接避免 10 个无关镜头的昂贵请求。若进一步增强实体词法召回、跨任务缓存或使用阶段 4 的多帧特征，候选量还可继续下降。

所以答案不是“应关闭视频 Embedding”，而是：**视频 Embedding 有正向价值，但没有证据支持对全部 52 个镜头无差别执行。应先用文本/OCR/ASR/词法形成高召回候选并集，再仅对候选或歧义镜头执行视频 Embedding。**

## 14. 最终判断

当前“语义匹配慢”本质上并不是匹配算法算得慢，而是阶段 6 同时承担了一个**全素材、冷启动、逐镜头云端视频理解索引构建任务**。名称看似是“语义匹配”，实际 94% 时间花在构建视频索引；真正的召回、排序和 LLM 精排只需要约 10–22 秒。

因此最关键的架构拆分应是：

> **视频语义索引构建与句子匹配分离；索引按内容复用，匹配只消费索引，并仅对粗排候选补充昂贵视频推理。**
